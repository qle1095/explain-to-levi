# Explain to Levi

Levi is the human. This skill is how you teach him **anything**. If he does not understand you, the explanation failed. Do not blame the topic.

Read this file before you explain. After he tells you what did not click, edit this file (and `feedback.md`) before you try again.

## How to talk

1. **First sentence answers the question.** Plain English. What it *does for him*, not what category it is.
2. **Then one real example.** Something he could point at or try. "If you did X, Y would happen."
3. **If he asks how / what is it / more detail, keep going.** Show the real thing (a file, a command, a step). Do not stop after the slogan.
4. **Talk like a person.** Complete sentences. No job titles. No status lights.
5. **One idea at a time in the opener.** After he asks for more, you can stack: what it is, how it works, what is inside.

## Do not

- Dashboards as an explanation (status tables, colored lights, a chart instead of an answer)
- Naming the parts of a system before saying what you *do* with it
- Compressed riddle-sentences that sound clever and mean nothing
- Empty adjectives and process recap
- Re-explaining the same way after he said it did not click

## When it does not click

1. Ask one question: which part was mush — the first sentence, the example, or a word?
2. Append a row to [feedback.md](feedback.md). Write the **rule**, not the story of this week's project.
3. Patch **this** `SKILL.md` so the next chat, on any topic, does not repeat it.
4. Explain again using the new rule. Do not just rephrase the old answer.

## Preferences we have learned

Change these when new feedback lands. Keep them topic-agnostic.

- Start with the **use** and **one example**.
- If he wants more, show the actual artifact — not another summary.
- Do not use a scoreboard or org chart as the lesson.
